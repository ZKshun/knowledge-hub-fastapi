## 接口

| 方法/路径 | 输入 | 响应 | 状态（已运行确认） |
| --- | --- | --- | --- |
| POST `/documents` | CreateDocumentRequest | 元数据 + content | 201 |
| GET `/documents` | 查询参数 | items/total/page/pageSize；items 只有元数据 | 200 |
| GET `/documents/{id}` | 字符串 ID | 元数据 + content | 200；不存在/已删除 404 |

## 创建、修改与查询

创建必填字符串：`title`、`content`。可选字段：`summary`、`categoryId`、`teamId`、`authorId`、`coverImage`、`tags`、`remark`、`createBy`（字符串），`status`（枚举数值）、`isPublic`（布尔）。

创建默认：`status=0`、`isPublic=false`、各计数 0、正文 `version=1`、`deleted=false`；初始 status=1 时设 publishTime。未提供 summary 时 PostgreSQL summary 仍为空，Mongo contentSummary 由正文生成；响应不会擅自补一个 summary。

修改字段与创建一致，但不接受 createBy，新增可选 updateBy。只有传入的字段更新。已实测：PATCH summary/categoryId/remark 为 null 可成功清空；title/content/status/isPublic 为 null 可返回 500；创建 title/content 为 null 则返回 400。创建时 createBy 同时写入 updateBy。

列表参数：`title`、`categoryId`、`teamId`、`authorId`、`status`、`page`、`pageSize`。page 默认 1，pageSize 默认 20、范围 1–100；page 必须 ≥1。title 使用 PostgreSQL ILIKE 匹配；排除 deleted=true；按 created_at 降序。相同时间的次序旧版无第二排序，不在差分比较中虚构稳定性。

status 查询仅作整数校验，创建/修改 status 使用枚举；二者不能自行统一限制。已实测：status= 转为 0 并返回 200；status=999 返回空列表；page= 返回 400；额外查询参数返回 400。

相同 created_at 的实际场景为 `075_list_tied_created_at`：两篇匿名文档的创建时间设为 2099-01-01，第三篇保持较早时间，再通过真实 GET 读取。对该场景使用 `assert_page_with_ties_equivalent`，只允许相同时间的连续组内部换序；组间顺序和每个字段仍严格比较。其他数组比较保持严格顺序。

## 状态、字段与副作用

| 状态值 | 名称 | v1 行为 |
| --- | --- | --- |
| 0 | 草稿 Draft | 可通过 CRUD 直接设置 |
| 1 | 已发布 Published | 创建或从非发布变发布时设置 publishTime |
| 2 | 已归档 Archived | 不引入 v6 审核；v1 没有异步索引 |

元数据字段：`id,title,contentId,summary,categoryId,teamId,authorId,coverImage,tags,status,remark,viewCount,likeCount,commentCount,favouriteCount,wordCount,publishTime,isPublic,createdAt,updatedAt,createBy,updateBy,deleted`。

`id` 以及 bigint 外键/操作者字段保持字符串或 null；contentId 为 ObjectId 字符串。详情/创建/修改附加 content；列表不附加 content。已确认最小创建与详情的可空元数据字段显式返回 null，字段集详见样例 001/003。

- 创建顺序：生成 ID→写 Mongo→写 PostgreSQL；SQL 失败时删除刚写的 Mongo 正文。
- 显式更新 content：Mongo 正文、contentLength、contentSummary 更新且 version+1，即使正文与旧值相同也递增；PostgreSQL wordCount 更新。空 PATCH 或仅元数据字段不触发正文版本递增。
- 仅更新 summary：同步 Mongo contentSummary，不增加正文版本。
- 改状态为发布：只有原状态不是发布时重设 publishTime；归档不自动清空原 publishTime。
- 删除：PostgreSQL 和 Mongo 都软删除；不物理删业务正文。
- 详情发现 Mongo 正文缺失时旧服务返回空 content；修改 content 找不到正文时抛出 400。

Python Task4内部扩展：成功正文带operationId，创建失败补偿后保留空正文deleted=true/creationFence=true标记，无对应SQL业务元数据。它防止迟到insert重建孤立正文，详见D021与[阶段报告](../versions/v1/task-4-report.md)。后续差分只可排除经过单独断言的内部标记和operationId字段，不能排除所有deleted文档或掩盖业务正文差异；原版软删除记录仍须完整比较。原服务物理删除补偿的历史证据保留，不覆盖成新实现输出。

Task5已实现修改/软删除和恢复：Mongo条件写入带version/operationId；补偿恢复公开版本但换成rollback:<operation_id>内部屏障，防迟到CAS复活。原软删除仍保留正文、版本不递增。旧正文/摘要的受控JSONB恢复快照采用可逆Base64编码，兼容BSON允许的NUL，null/空串不混淆；不改变HTTP或Mongo业务字段（D023–D024，[Task5报告](../versions/v1/task-5-report.md)）。Task6已完成HTTP与双库差分，Task7在全新隔离双库回归。

Task5用例对PATCH非空列的显式null抛InvalidDocumentChange；Task6已保持原500，不能仅凭这个内部异常名字改成400。正文缺失修改仍为DocumentContentNotFound→400，文档不存在/已删除为DocumentNotFound→404；DTO校验错误按原400协议适配。

创建空title原版201，创建空content原版500（Mongoose required string）；PATCH空content可成功。Task4按创建专用校验实现，Task6对应HTTP已通过原证据差分。发布时间来自JS Date，保持毫秒精度；其他SQL timestamp列型不变。

BIGINT字段只有字符串DTO校验，旧transformer原样交PG：PG16接受0x10/0o10/0b10并规范化存储，拒绝全角/阿拉伯数字、NBSP包裹值和溢出。Task4已用真实库回归并统一外键/操作者、查询及锁键原生CAST（D022）。外部仍为字符串，不能先用Python int或strip扩大/缩小接受集合；Task6已适配HTTP错误格式。

## 字数与预览

旧版摘要：正文 trim、连续空白折叠为一个空格，最多截取 200 个 JavaScript UTF-16 单元，超出追加 `...`。`contentLength` 使用 JavaScript string.length，补充字符（如 emoji）计两个单元。

旧版 wordCount：先计 U+4E00–U+9FFF 汉字数量，再去汉字、按空白分段计剩余非空 token。不是标准中文分词，标点也可能被计为 token；不能换成“更智能”的算法改变结果。Python 空白分类、trim 与 UTF-16 截断都要用兼容样本确认。

Task 2 已对固定源码编译产物做纯方法探测并实现单元测试：BOM U+FEFF 为 JS 空白，NEL U+0085 和 U+001C 不是；`a`×199 后接 🧠 的原始摘要包含半个代理字符 U+D83E。既有 HTTP/数据库快照中的 U+FFFD 来自 Node BSON 编码，Task 3 必须在映射边界复现该替换。纯规则通过不代表 HTTP/BSON 差分已经通过。

Task 3已在真实Mongo中写入并读回该摘要，与044原版快照逐值比较U+FFFD替换通过；原SQL列型/默认值、读取关联、分页与软删除路径也已在隔离双库验证，见[阶段报告](../versions/v1/task-3-report.md)。Task4–5补齐恢复，Task6另以原版POST/GET及选定双库状态证明Node pg文本也执行相同替换；API原输入和持久化读回的差别保留。

## 校验与错误

全局 ValidationPipe 使用 whitelist=true、transform=true、forbidNonWhitelisted=true。错误 body 的 message 数组及顺序、error 文本要采集，不允许默认暴露 422/detail。

已知业务错误文本：`Document {id} not found`；修改正文缺失时 `Document content {contentId} not found`。数据库异常文本不得从源码臆造，需要将有意义的外部差异记录并按兼容策略处理。
