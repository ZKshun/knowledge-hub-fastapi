# v1 一页报告：做了什么，链路怎样闭合

**范围**：v1 已完成文档创建、查询、修改和软删除，并在本地验收后合并 main。README 中的上传、检索和 RAG 问答是后续版本目标，目前尚未实现。

## 一条主链路

```text
请求 → 兼容旧版的解析/校验 → FastAPI 文档接口 → 业务用例
     → PostgreSQL 元数据 + MongoDB 正文 → 原版格式的响应
                                  ↘ 写入失败 → 操作日志核对 → 补偿或等待恢复
```

| 用户要做什么 | 服务怎样完成 | 用户看到的结果 |
| --- | --- | --- |
| **创建** | 生成字符串文档 ID；先记操作日志，再写 Mongo 正文和 PostgreSQL 元数据；两库 ID 互相关联 | 返回 **201** 和完整文档，正文初始版本为 1 |
| **列表/详情** | 列表从 PostgreSQL 筛选、分页；详情再按 `contentId` 取 Mongo 正文 | 列表不带正文；详情带正文；找不到或已删除返回 **404** |
| **修改** | 锁住文档并读取最新值，只改请求中实际提交的字段；正文写入用版本和操作 ID 限定 | 返回 **200**；即使提交相同正文，正文版本也加 1；只改元数据不加正文版本 |
| **软删除** | PostgreSQL 与 Mongo 都标记删除，保留业务正文 | 返回 **200**；之后详情和重复删除为 **404**，列表不再显示 |
| **写入出错** | PostgreSQL 操作日志记录未决状态；恢复时先确认原事务是否提交，再决定保留结果、条件补偿或等待重试 | 不把不确定结果当成功，也不盲目删除可能已提交的正文 |

实现入口是[文档接口](../../../src/knowledge_hub/modules/documents/api/router.py)，双库读写集中在[存储实现](../../../src/knowledge_hub/modules/documents/infrastructure/document_store.py)，失败核对在[恢复服务](../../../src/knowledge_hub/modules/documents/infrastructure/recovery.py)。

## 怎么确认完成

- **对照旧版**：固定 NestJS v1，重放 **75** 项 HTTP/双库证据，另核对 **71** 项传输边界；对外字段、状态码、错误和两库副作用逐项比较。
- **跑通真实路径**：连续执行创建→查询→修改→删除→404，并直接核对 PostgreSQL 与 MongoDB 的关联、版本和删除状态。
