# FastAPI 重构总体设计

日期：2026-10-28。状态：总体方向已由用户接受；本文件将已确认决定落文档，版本实施细节按各版规格和计划推进。

## 目标与动机

把现有企业级 RAG 知识库服务端由 NodeJS + NestJS 重写为 Python + FastAPI。以原项目各版本最终文件树和真实行为为功能依据，逐版形成可运行、可测试的闭环。强调清楚的目录、单一职责、小文件、稳定接口和跨会话接续能力。

成功标准：现有前端无需为框架迁移修改调用协议；对应版本请求、响应、错误、权限和异步行为经过对比验证；新工程师能从 README 和 AGENTS 进入当前任务；任一中断点有足够证据恢复。

## 已选择方案与取舍

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 保留接口与多数据库，按业务模块重建内部结构 | 需要处理跨库一致性，但能减少前端和数据迁移变量 | 用户已选择 |
| 同时合并数据库和重定接口 | 运维可能简化，但将增加功能行为与数据迁移变化 | 不纳入本次重构 |
| 从第一版拆成多个微服务 | 独立扩容方便，但增加部署、通信与追踪成本 | 采用模块化单体与独立 Worker |

业务实现不照搬 NestJS Controller/Service 文件布局。接口入口只做适配；业务用例负责事务编排；数据库与第三方依赖通过接口隔离。

## 范围

- 按 [路线图](roadmap.md) 从 v1 开始，覆盖文档、解析、异步索引、审核、身份权限、搜索、图谱、RAG、会话、记忆、Agent、评测及互动通知。
- 保留 PostgreSQL 元数据、MongoDB 正文、ES 文档与块索引、Neo4j 图谱、Redis 缓存、RabbitMQ 消息、RustFS 对象的职责。
- 保留既有 API 路径、camelCase JSON、字符串 ID、状态语义、错误结构和 AI SDK 流式协议。
- 建立工程质量门禁、可执行迁移、测试、操作文档和版本交接记录。

## 非目标与禁止事项

- 不以重构名义扩展产品需求，不一次实现所有版本，不重写前端。
- 不将 ES 向量索引擅自替换为 pgvector；Compose 使用 pgvector 镜像不代表现有向量数据放在 PostgreSQL。
- 不清理旧 NestJS 大文件；300 行硬限制针对新 Python 生产代码。
- 不默认复用已有运行库和数据卷进行测试，不写真实用户数据或把凭据放进文档、快照。
- 不把有文档、能启动、单元测试通过等同于版本验收通过。

## 工程与流程约束

版本分支一律从最新 main 派生，验收后回 main。完整分支顺序、并行约束和中断恢复见 [SOP](agent-sop.md)。

新代码每生产文件最多 300 物理行（含空行和注释），目标 200；内部 snake_case，外部 camelCase。格式、类型、覆盖率、架构依赖和文件行数在 CI 执行，见 [规范](code-standards.md)。

总体采用 Python 3.12 与 uv；依赖在 v1 建环境时选择经验证兼容的版本并锁定。保留异步 I/O；CPU 密集解析转 Worker。进程池、消费者库等普通实现细节由实施者基于版本需求决定，并记录原因。

## 一致性与企业使用边界

PostgreSQL 与 MongoDB 没有天然的同一事务，v1 就要明确失败补偿和可恢复记录。从 v3 引入事务 Outbox、任务状态、幂等和死信；按文档内容版本防止乱序和过期任务覆盖新状态。索引是可重建派生数据。

权限接口按原版在 v7、v9、v15 逐步交付。前期版本是受控开发里程碑，不能当成已经具备最终企业权限的生产版本。v15 必须验证文档、全文、向量、图谱、引用和缓存的同一可见性规则。

从 v11 起建立固定 RAG 基线数据，v19 扩展为完整评测观测。模型结果允许自然语言变化，权限、引用来源、检索次数、工具路由和失败行为使用明确断言。
