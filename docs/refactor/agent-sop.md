# Coding Agent 开发与跨会话 SOP

本文件给没有聊天上下文的 Agent 使用。用户已确认总体架构、版本映射、分支规则和兼容要求；不要重复要求用户选择相同方案。

## 1. 开工与恢复

1. 读根目录 `AGENTS.md`、README、本文件和 [status.md](status.md)。
2. 读状态中的当前版本规格、实施计划、契约；仅对本次任务按 AGENTS 路由补充专题规则。
3. 在 Python 仓库检查 `git status --short --branch`、`git branch --show-current`、`git log -n 5 --oneline`、`git diff`。保存当前 SHA、分支和已有变更的归属。
4. 用真实文件/提交核对 status：未提交代码、已提交但未合并、依赖缺失、测试未跑分别记录；文档与 Git 冲突时先核实并修正文档，不覆盖现有改动。
5. 找到计划中的第一个未完成任务，确认前置接口存在。汇报接续点并继续；只在需要新业务决策或存在不可安全处理的冲突时询问用户。

必要信息全部在仓库中；不依赖“上一轮已经说过”、Agent 私有记忆或另一个会话继续运行。

## 2. 版本分支规则

每个 `vN` **必须从 main 创建**。只有前版已验收并合并 main，才能开启下一版。

新版本的一般命令如下；先检查工作区清洁与远端配置，不能把示例机械执行到错误仓库：

```bash
git switch main
git pull --ff-only origin main
git switch -c vN main
```

- 没有 remote 时省略 pull，明确记录“仅本地 main”，不得虚构已同步远端。
- 当前版本分支已存在时核对来源并恢复该分支；禁止同名重建、强推或重置覆盖。
- 禁止从未合并的 vN 直接派生 vN+1；main 后续发生变化时，先检查变更，再将 main 合入当前版本并重新验证。
- 所有受版本控制的开发文档和代码在 vN 更新；main 仅接收已验收版本。仓库首个空 main 提交仅用于建立分支起点，不含业务实现。
- 独立 worktree 用于隔离有冲突的工作；仍须遵守 vN 来源规则，不能把旧 NestJS 分支作为 Python 分支祖先。
- 同一版本可以跨多个对话接续，但同一工作树同时只有一个写入者。多个 Agent 同时写时必须明确文件所有权或使用隔离工作树，并统一集成验证。

用户已明确要求逐版开发完毕后合并 main，该既定流程包含验收通过后的本地合并授权，无需每版重复询问。确认所有验收项通过后执行：

```bash
git switch main
git merge --no-ff vN -m "merge: integrate vN"
```

合并后检查工作区和关键回归，记录合并 SHA。版本分支保留用于追踪；如打标签，采用 `milestone/vN` 避免与分支同名；标签、推送和远端 PR 根据用户授权执行。禁止将“建议合并”写成“已合并”。

Windows 环境如果沙箱与宿主账户不同，可能遇到 `.git/index.lock` 权限或 dubious ownership：通过正式审批执行需要的 Git 写操作；必要时仅对具体命令使用精确 `safe.directory`，不得全局信任通配目录或通过切换工具绕过审批。

## 3. 版本准备与事实提取

1. 确认本版来源 SHA 和前版 main 验收记录。
2. 对比旧版最终文件树，列出新增与变化接口、字段、持久化、消息、权限、配置、失败行为。
3. 创建/更新 `docs/versions/vN/spec.md`、`docs/contracts/vN.md`；范围必须与 roadmap 一致。
4. 对未验证行为标“源码推导/待运行验证”，不能伪造确定契约。
5. 按 [兼容策略](compatibility.md) 建立隔离原版基线；不能切换有用户变更的参考工作区或误用旧构建产物。
6. 制定可逐项实施的计划，写出文件职责、接口签名、断言、命令和预期结果。沿用已确认方向，具体工程细节由 Agent 落实。

整体需求/协议变化需用户决定；普通文件拆分、函数实现和依赖锁定有技术依据即可记录，不重复请求许可。

## 4. 实现循环

每个任务按“契约/失败用例 → 实现 → 验证 → 记录”推进：

1. 为业务行为或缺陷建立有意义的失败测试，检查失败原因正确。
2. 实现最小完整用例；生产代码遵守模块边界、300 行硬限制和类型要求。
3. 跑受影响测试，再执行本任务所需集成或契约验证；成功后更新计划勾选。
4. 在阶段边界同步 status 和工作日志；按当前授权提交完整的小步变更，不混入无关工作。
5. 扩大验证只在变更风险需要时执行。单纯文档修改验证链接、规则覆盖和 Git diff 即可。

依赖由锁文件管理；不能在不同会话各自临时安装不一致版本。测试环境采用独立数据库、索引、队列、bucket 和隔离端口，不删除既有数据卷或启动同名容器争用端口。

## 5. 每版验收

以 `docs/templates/version-record.md` 生成 `docs/versions/vN/acceptance.md`，至少包括：

- 范围内功能和完整用户路径逐项通过；与原版差异已清楚判定。
- 保存逐项“需求→实现方式/关键位置→验证证据→结果”对照；版本交付时用同一对照向用户说明做了哪些需求、分别怎么完成，不以提交或文件列表代替需求汇报。
- 按[版本记录模板](../templates/version-record.md)提供`docs/versions/vN/implementation-flow-report.md`：逐项串起需求、用户触发、HTTP/任务入口、用例/适配模块、存储或外部副作用、失败/恢复、响应和测试证据；明确哪些链路尚未实现或验证。该报告面向接手工程师和用户，代码路径应可点击核对。
- HTTP/JSON/错误/数据库/MQ/流式按本版变化完成契约和副作用验证。
- 必要的迁移、恢复/补偿、幂等、权限和异常测试通过；前版回归未破坏。
- 格式、lint、严格类型、生产行数、85% 覆盖率和本版集成/E2E 全部有真实输出。
- README 的启动和测试步骤已实测；配置样例、规格、契约、决策与实际实现一致。
- 审查未提交差异、敏感信息、无关修改、测试跳过和已知限制。

模拟测试不能代替真实集成验证；关键项没跑或失败则状态保持 implementing/verifying/blocked，不写 accepted。代码审查可由独立 reviewer 或本会话完成，记录是谁、依据和未解决问题；没有审查证据不声称“已独立审核”。

## 6. 中断与交接

结束会话、等待用户/基础设施或切换版本前必须：

1. 更新 `status.md`：当前版本、阶段、分支/SHA、已完成、未完成、阻塞、下一条可执行任务和文档入口。
2. 更新计划勾选；未运行的验证保持未完成，不以代码存在推断通过。
3. 追加 `work-log.md`：日期、操作、关键文件、实际命令结果、决策/偏差、未提交变更和进程/容器。
4. 复杂中断使用交接模板保存 `docs/versions/vN/handoff-<date>.md`，status 指向它；同日多次用递增序号避免覆盖。
5. 告诉用户完成什么需求、分别怎样完成、验证什么、还差什么，以及下次从哪个入口继续。版本完成时附上实现链路报告；阶段交接明确本轮只是阶段成果。不能只让用户去另一个聊天寻找上下文。

`status.md` 是当前状态的唯一摘要；工作日志追加历史，规格记录目标，计划记录任务，验收记录证据。四者各有职责，不能用日志覆盖当前待办。

## 7. 状态机与完成定义

```text
planned → implementing → verifying → accepted → merged
                   ↘ blocked ↗
```

blocked 必须写明具体原因、已尝试安全操作和解除条件。accepted 表示版本功能及门禁通过；merged 表示已核实进入 main。旧版已 merged 才能创建新版本。本轮的 v1 文档完成不代表 v1 accepted。

状态不以固定提交 SHA 自引用：状态文件可记录“本次变更前的核验 SHA + 当前分支”，下一会话先运行 Git 获取实际 HEAD。验收和合并记录保存可验证的实现/合并 SHA。

## 8. 文档维护与渐进披露

- AGENTS 只保留硬约束、读取顺序、路由和冲突规则；细节放专题文档，不不断堆进入口。
- 修改规则必须同步决策记录与受影响专题；新文件加入对应入口，检查相对链接。
- 根 README 的业务闭环描述最终目标；运行说明与状态只能描述已经验证的现状。
- 历史事实标日期与 SHA；禁止把当前参考工作区分支或 `origin/main` 名字当成永不变化的依据。
